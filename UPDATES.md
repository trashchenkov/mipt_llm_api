# Новые версии библиотек: что меняется в примерах

Актуализация на **16 ноября 2026 года**.

Блокноты используют версии из `uv.lock`: `uv sync` устанавливает именно их.
В пояснениях рядом с примерами указано, как отличается поведение новых библиотек.
Для выполнения занятий обновлять окружение не нужно.

## Какие версии сравниваются

| Компонент | В блокнотах | Новые версии, к которым относятся пояснения |
|---|---|---|
| GigaChat Python SDK | `0.2.3` | `0.2.4`; для нового адаптера LangChain — `0.3.0a1` |
| Адаптер `langchain-gigachat` | `0.5.1`, API v1 | `0.5.3a1` + SDK `0.3.0a1`, API v2 включается параметром `use_api_v2=True` |
| Прокси GPT2GIGA | `0.3.0` | `0.3.2`; режим gateway — в `0.3.3a1` |

Суффикс `a1` обозначает предварительный альфа-выпуск. На указанную дату стабильными
оставались SDK `0.2.4`, адаптер `0.5.1` и GPT2GIGA `0.3.2`.
Установка стабильного адаптера поэтому не даёт возможностей, описанных для `0.5.3a1`.

## Первое занятие: SDK и формат HTTP-запроса

### Ограничение длины ответа: `max_tokens` (§ 2.4)

В GigaChat API v2 параметры генерации передаются внутри `model_options`:

```python
{"model_options": {"max_tokens": 10}}
```

В SDK `0.2.3` параметр `max_tokens` на верхнем уровне уходит на сервер без переноса.
Сервер v2 игнорирует его, и ответ может оказаться длиннее заданного лимита.

SDK `0.2.4` сам переносит верхний `max_tokens` в `model_options`.
Поэтому при работе через эту библиотеку оба варианта задают лимит.
Изменилось поведение Python-библиотеки; в HTTP-запросе параметр по-прежнему должен
находиться внутри `model_options`.

### Проверка режима вызова функции (§ 7.6)

Параметр `tool_config.mode` определяет, может ли модель вызвать функцию и обязана ли она это сделать.
SDK `0.2.4` проверяет допустимость значения до отправки запроса. Опечатка в режиме приводит
к ошибке библиотеки. В опыте с `0.2.3` неизвестный режим доходил до сервера,
который обрабатывал его как `auto` — модель сама решала, нужен ли вызов.

Таким образом, проверка SDK и проверка сервера — разные этапы обработки запроса.

## Первое занятие: GPT2GIGA и история Responses (§ 11)

GPT2GIGA переводит запросы библиотек OpenAI и Anthropic в запросы к GigaChat.
В формате Responses диалог можно продолжать двумя способами:

1. Передавать всю историю в `input` каждого запроса. Так сделано в блокноте с GPT2GIGA `0.3.0`.
2. Передать `store=True`, а в следующий запрос — `previous_response_id`, ID предыдущего ответа.
   Историю хранит сервис; повторно отправлять все сообщения не нужно.

Второй способ доступен в GPT2GIGA `0.3.2` с GigaChat API v2.
В этой версии запрос к API v1 с `store=True` отклоняется с HTTP 400.

### native: один продолжающийся диалог

В режиме **native** историю хранит GigaChat. Прокси использует идентификатор диалога
GigaChat (`thread_id`), поэтому ID разных ответов может совпадать.

Например, после сообщения «Едем в Казань» вы спрашиваете о поездах. История теперь содержит
и выбор города, и обсуждение поездов. Новый запрос по ID первого ответа продолжит
эту же, уже дополненную историю. Этот ID не позволяет вернуться к состоянию до обсуждения поездов.

Режим доступен в стабильной GPT2GIGA `0.3.2`.

### gateway: история для каждого ответа и отдельные ветки

В режиме **gateway** историю сохраняет сам прокси. Каждый ответ получает новый ID,
к которому привязана история на этот момент. При продолжении прокси выбирает её
по `previous_response_id` и передаёт модели.

Например, ответ на «Едем в Казань» получил ID `R1`. Обозначение `R1` здесь условное.
От него можно создать две ветки:

```text
«Едем в Казань» → ответ R1
                  ├─ previous_response_id=R1: «Подбери поезд»
                  └─ previous_response_id=R1: «Подбери самолёт»
```

Обе ветки начинают с одной и той же истории. Ветка про самолёт не содержит обсуждения поездов.
Сам по себе выбор gateway не заставляет приложение создавать ветки: оно должно передать
ID того ответа, от которого хочет продолжить разговор.

Режим есть в предварительной GPT2GIGA `0.3.3a1` и включается переменной окружения:

```dotenv
GPT2GIGA_RESPONSES_STORAGE_MODE=gateway
```

В стабильной `0.3.2` этой настройки нет.

## Первое занятие: сведения о кэше (§ 12)

В формате Anthropic Messages GPT2GIGA `0.3.0` возвращает только `input_tokens` и `output_tokens`.
В `0.3.2` в `usage` также передаётся `cache_read_input_tokens` — число входных токенов,
прочитанных из кэша.

Например:

```json
{"input_tokens": 38, "cache_read_input_tokens": 1470, "output_tokens": 2}
```

Полный вход в этом примере — **1508 токенов**: 38 обработаны заново, 1470 взяты из кэша.
Выход — 2 токена. Это пример счётчиков, а не постоянные значения: они зависят от запроса
и наличия подходящей истории в кэше.

## Первое занятие: выбор GigaChat API v1 или v2 (§ 13)

В GPT2GIGA `0.3.2` для встроенных моделей GigaChat префикс адреса прокси выбирает версию API:

- `/v1` — GigaChat API v1;
- `/v2` — GigaChat API v2.

Клиент продолжает пользоваться форматом OpenAI или Anthropic, а прокси переводит запрос
в выбранный формат GigaChat. Обновить пакет недостаточно: нужно также выбрать нужный адрес.
В блокноте используется GPT2GIGA `0.3.0`, направляющая запросы в GigaChat API v1.

## LangChain: что даёт адаптер с API v2

Относится к § 14 первого блокнота и § 6 второго.

Адаптер `langchain-gigachat 0.5.1` работает через GigaChat API v1.
Предварительный адаптер `0.5.3a1` с SDK `0.3.0a1` позволяет выбрать API v2:
при создании `GigaChat` задаётся `use_api_v2=True`.

### Можно потребовать вызов инструмента

В `bind_tools` режим `tool_choice="auto"` оставляет решение модели: вызвать инструмент
или ответить текстом. Режимы `"any"` и `"required"` требуют хотя бы одного вызова;
конкретный инструмент модель выбирает сама.

Например, перед ответом о вместимости аудитории агент должен обратиться к справочнику.
Приложение задаёт режим требования вызова, а модель выбирает функцию и её аргументы.
Требование вызова не гарантирует, что аргументы правильные: их по-прежнему проверяет приложение.

В адаптере `0.5.1` режима `"any"` нет. Middleware из § 6.1 повторяет просьбу вызвать
инструмент, но не гарантирует вызов. В `0.5.3a1` с API v2 для этого есть режим API.

### Параметр функции может допускать несколько типов

Аннотация `capacity: int | str` означает, что функция принимает число или строку.
В JSON Schema варианты записываются через `anyOf`.

Адаптер `0.5.1` отклоняет такую схему до отправки. Адаптер `0.5.3a1` с API v2
передаёт её серверу; допустимый аргумент — например, `{"capacity": 30}`.
Поэтому фильтрация таких инструментов в § 6.3 относится к старому адаптеру.

### Один ответ может содержать несколько вызовов

При `parallel_tool_calls=True` ответ модели может содержать, например, два вызова
`get_room_info` для разных аудиторий. У каждого вызова свой ID.
Приложение выполняет функции и передаёт каждый результат с ID соответствующего вызова.

Несколько вызовов в ответе ещё не означают одновременного выполнения функций:
последовательно или параллельно их запускать, решает приложение.

### Можно задать структуру ответа модели

Вызов `with_structured_output(..., method="json_schema")` задаёт схему итогового ответа.
Например, ответ должен содержать код аудитории и число мест. Если схему задать
Pydantic-моделью, адаптер разбирает ответ в объект этого класса и проверяет поля.

Это схема ответа модели. Схема аргументов инструмента описывает данные для вызова функции;
это другое место применения JSON Schema.

### Системное сообщение остаётся первым

В обоих API GigaChat системное сообщение должно находиться в начале истории.
Если добавить его между репликами диалога, сервер возвращает HTTP 400.
Для подсказок по ходу работы агента в примерах используется `HumanMessage`.
